# Архитектура: «Умный поиск» для store.softline.ru (MVP под 45 часов)

Хакатон «ИИ Кузница», трек «Аналитик данных». Задача: «Умный поиск на сайте» (Софтлайн, B2B-магазин ПО и ИТ-оборудования для юрлиц).

## Контекст для переиспользования в других сессиях

**Сроки.** Сдача 28.11.2026 10:00 (code freeze в 08:00). Стенд обязан работать 24/7 до 03.12 23:59 (включая питч). Питчи 02.12. До объявления итогов (15.12) организатор может попросить поднять стенд повторно в течение 24 ч. Q&A с организаторами 27.11 10:30. Бонус «Выбор заказчика» +6 баллов.

**Что требуется (из ТЗ и ответов организаторов).**
- Понимание смысла, синонимов, опечаток, сленга и аббревиатур. Пример: по «сервер» показывать серверное оборудование, а не ПО для сервера.
- Контекст: категория, сегмент, история клиента (один запрос от разных людей даёт разную выдачу).
- Ранжирование: релевантность + популярность + маржинальность.
- В выдаче минимум 4 товара.
- Допродажа (cross-sell, up-sell) на основе каталога и проверенных внешних источников (сайты вендоров).
- Ценовая выгода и акции в выдаче.
- Подсказки: автодополнение, исправление опечаток, связанные запросы. Бонус: товары в подсказках во время ввода.
- Интерфейс: поисковая строка достаточна (диалог не обязателен), на демо должно быть видно, что происходит с запросом по шагам.
- Аналитика равноправна поиску: логирование действий агента, разбор неудачных поисков, пробелы каталога и синонимов, измеримый бизнес-эффект, замкнутый цикл улучшений.
- Пять ролей: покупатель, менеджер e-com, продукт-менеджер, контент-менеджер, руководитель e-com.
- KPI организатора: доля запросов без результата, уходы после неудачного поиска, конверсия поиска в заказ, потеря онлайн-заказов.
- Отдельное демо (mock-API допустим), открытый репозиторий, любые open-source модели и внешние API с учётом лицензий. Перечень моделей указывается при сдаче.
- Обязателен расчёт стоимости одного запроса по шаблону организатора (файл в облаке со ссылкой без авторизации).
- Нет требований по внутреннему контуру, времени ответа и бюджету на запрос.

**Статус документа.** Упрощённая под 45 часов архитектура (MVP-контур). Контракты API ведутся прямо в Pydantic-моделях FastAPI с автогенерацией OpenAPI и TypeScript-типов (без 17 отдельных JSON-схем и кодогенераторов). 6 критериев жюри («Положение», Приложение 1) и выгрузка «данных с метрики» проверяются на Google Drive задачи в первые 3 часа.

## 1. Стек и модели

### Принцип

**Детерминированное ядро плюс LLM как улучшатель.** Весь путь «запрос → ≥4 товара» должен работать без единого внешнего вызова. LLM поднимает качество на сложных запросах, но не является точкой отказа. Из этого следуют и 24/7, и честная экономика запроса.

### Выбор

| Слой | Выбор | Обоснование | Отвергнуто на MVP |
|---|---|---|---|
| API и контракты | Python 3.11, FastAPI, Pydantic v2 (единый источник истины). Из `/openapi.json` генерируются TS-типы (`openapi-typescript`). Индексы грузятся `np.load(mmap_mode='r')` | Нулевые накладные расходы на поддержание контрактов; SSE для стриминга trace | Микросервисы; ручное ведение 17 JSON-схем, `extract_contracts.py` и `make_mock.py` |

## 2. Индексация и обогащение данных

### 2.1 Модель сущностей

Единый реестр `entities`:
- `BRAND` — вендор.
- `FAMILY` — group, страница продукта.
- `CATEGORY` — узел дерева (9 311 узлов; многие листья являются продуктами).
- `PRODUCT_TYPE` — закрытая таксономия, ≈50–80 узлов.
- `CONTENT` — разделы и страницы сайта (вебинары, лендинги вендоров) из `vendorUrl` фида и ручного seed.
- `EXTERNAL_PRODUCT` — продукт вендора из curated seed, отсутствующий в каталоге (источник `catalog_gap`, например MDaemon).

Каждая сущность имеет алиасы (`alias`, `kind`, `status ∈ {seed, verified, auto, proposed}`, `evidence`, `source`). Для ранжирования используем `verified/auto/seed`. `proposed` проходит через тикет (п. 4).

### 2.2 Пайплайн ingest

**I0. Парсинг.** `iterparse` с `clear()`. Выход: `offers.parquet`, `categories.parquet` (дерево с `path`, `depth`, `root_id`), `params_long.parquet`. HTML-entities и CDATA в `description` и `name` раскрываем.

**I1. Нормализация полей.**
- Плейсхолдеры в params («другое или отсутствует», «не определено» в любом регистре) → NULL.
- Цена: `price<=0` → `price_state='on_request'`, `price_rub=NULL`.
- Скидка: `oldprice>price>0` → `discount_pct`. `oldprice==price` — акции нет. `oldprice<price` — флаг ошибки данных. Скидка выше 70% — подозрительная, в выдачу не выводим.
- `description` парсим по разделителю « • » и ключам «Ключ: значение».
- Название: срезаем дублирующий префикс вендора. Вычленяем `product_name_clean`, `license_program` (VIP, Enterprise), `term`, `qty` («25 лицензий»), `version`, `edition`.

**I2. Порядок доверия при конфликтах.** Для сегмента: `Тип организации` вместе с ключевыми словами в name приоритетнее поля `Пользователь` и ключа description «Тип клиента». Каждый конфликт пишем в `data_quality_issues` (вклад в аналитику контент-менеджера).

**I3. Family-слой.** `family_id = group_id` (если нет — `o:{offer_id}`). Для каждой family считаем:
- `representative_offer`: доступный, `price>0`, коммерческий сегмент, максимальная версия.
- `n_variants`, `variant_axes` (срок, тип лицензии, сегмент, qty).
- `available_any`, `price_min` и `price_max` (только по `price>0`), `discount_best`.
- `data_quality_score`: картинка, полнота params, читаемость названия, отсутствие конфликтов.

**I4. Класс продукта (упрощённо: правила + точечный LLM).**
1. Детерминированные правила на базе `Тип продукта`, `Тип поставки`, корня/пути категории и наличия hardware-параметров (Форм-фактор, Совместимый сокет, Семейство процессоров, УправлениеVLAN) покрывают ~85–90% каталога за секунды.
2. LLM вызывается **только для оставшихся неоднозначных/крупных категорий** (несколько сотен узлов вместо всех 9 311).

Результат — `product_class ∈ {software, hardware, cloud_service, subscription, certificate, training/webinar, other}` и `product_type` из закрытой таксономии.

**I5. Обогащение family через LLM (только топ и демо).**
- **Охват:** прогоняем LLM-обогащение батчами только для **топ-500–1000 популярных family** (по структурному prior) и family, относящихся к демо-сценариям и ключевым вендорам. Хвост каталога не обогащается и ищется по очищенным именам, BM25F, char-3gram и эмбеддингам.
- На входе — очищенное имя, вендор, путь категории, лучшие params и до 300 символов description.
- Выход (JSON, валидация Pydantic): `canonical_name_ru`, `canonical_name_en`, `aliases[]`, `typical_queries[]` (5–6 штук), `use_cases[]` (3 фразы), `buyer_roles[]`, `is_ru_registry` (по реальному полю реестра), `analogs[]` и `complements[]` (кандидаты для графа).
- Контроль галлюцинаций: алиас становится `auto`, только если фонетически/строково близок к имени или бренду, либо подтверждён curated seed. Остальное получает `proposed`.

**I6. Артефакты для поиска.**
- Лемма-индексы по полям: `name_head` (до « для »), `name_target` (после « для », вес мал: «Антивирус для сервера» не конкурирует с серверным железом), `brand`, `category_path`, `aliases`, `params_values`, `description`.
- Char-3gram индекс по `brand + name_head + aliases` для fuzzy.
- Фонетический ключ транслитерации для брендов и алиасов.
- Словарь SymSpell по леммам каталога и алиасов.
- Эмбеддинги family (`canonical_name + type + use_cases + category_path`). Считаются один раз на GPU (Colab/Kaggle).
- Trie/отсортированный массив префиксов для typeahead с весами.
- Статические «Популярное» по корневым категориям (12 штук на корень) — нижний fallback.

**I7. QC-отчёт ingest** (отображается на вкладке Ops & Cost): доли `price_state`, валидных акций, `available`, конфликтов, family без картинки, распределение `product_class`, покрытие gold-запросов.

### 2.3 Внешние источники (вендоры) — Curated Seed вместо краулера

Автоматический краулер по 30 сайтам на 45-часовом хакатоне несётся высокий риск блокировок и потери времени. Поэтому:
- **Основной источник:** вручную/полуавтоматически собранный **curated seed (`vendors_seed.yaml`) по 8–12 ключевым брендам** (включая бренды из gold-10, 1С, Kaspersky, Astra Linux, Киберпротект, Positive Technologies, MDaemon).
- Для каждой связи (`complements`, `upsell_to`, `analog_of`) и сленгового алиаса зафиксированы реальные `evidence_url` и короткий сниппет (до 200 символов) с официального сайта вендора.
- Для демонстрации технической возможности автоматического сбора в репозитории прилагается рабочий скрипт извлечения на базе `httpx + trafilatura` на примере 1–2 эталонных страниц вендоров.

### 2.4 Цены и акции

- **Нормализация единицы.** Из `qty` и `term` считаем цену за пользователя/узел за год (если не распознаны — не сравнивается).
- **Сравнимые позиции** (`comparable_key`): тот же `product_type`, сегмент, тип лицензии и нормализованные qty/term (минимум 3 позиции в выборке).
- **Бейджи:**
  - «Акция −X%» — только при валидном `oldprice > price > 0` (`0 < discount ≤ 70%`).
  - «Выгоднее аналога на Y% за пользователя/год» — сравнение **только внутри каталога** по рёбрам `analog_of` и `comparable_key`, с подписью основы («по сравнению с N позициями каталога»).
  - «Цена по запросу» — `price_state=on_request`.
- Отдельный провайдер внешних цен (`ExternalPriceProvider`) из MVP исключён (упоминается только как точка расширения в будущем).

### 2.5 Граф допродаж

Рёбра: `complements`, `upsell_to`, `analog_of`, `requires`, `integrates_with`. Каждое ребро содержит `source ∈ {vendor_evidence, catalog_structure, llm_validated, co_click}`, `evidence_url`, `snippet`, `confidence`.
- **Источники:** матрица допустимых пар типов (ОС→антивирус, ОС→бэкап, ОС→виртуализация и т.п.) + curated seed вендоров (`vendor_evidence`) + `llm_validated` для топ-500 family.
- **Правила выдачи:** допродажа не показывает недоступное и `price=0` как основное предложение, учитывает сегмент и исключает уже купленное (из истории). До 3 позиций на блок, разные типы.

### 2.6 Честная работа с отсутствующими данными

| Признак | Источник (приоритет по убыванию) | Метка |
|---|---|---|
| Популярность | реальные клики (Метрика, если найдётся; живые клики демо) → структурный prior (log числа вариантов, доля доступных, вес вендора по SKU) | `real` / `proxy` |
| Маржа | `margins.csv` (если появится) → ручные веса по категориям от e-com менеджера → нейтральное значение | `real` / `proxy` / `simulated` |

- Маржа работает только как тай-брейкер внутри «полосы» близкой релевантности (`|rel − rel_лучшей_в_ярусе| ≤ δ`) и никогда не ломает релевантность.
- Любая симулированная метрика или модельный расчёт на дашбордах помечается явным тегом (`real / derived / simulated / modeled`). В trace каждая фича несёт `source`.

### 2.7 Hot-overlay (замкнутый цикл)

Базовый индекс неизменяем (`IndexState`). Поверх лежит версионируемый overlay в SQLite: `synonyms`, `aliases`, `pins/demotes/boosts`, `intent_priors`, `catalog_patches`.
- Применение правки — атомарная подмена ссылки `OverlayState` (без переиндексации и рестарта, за миллисекунды).
- Каждая правка увеличивает `config_version`, пишется в аудит и позволяет мгновенный откат на предыдущую версию.

### 2.8 Eval-набор и сравнение (упрощённая оценка качества)

- **10 gold** (нейтральный контекст) — как smoke-тест, демо и жёсткий регрессионный якорь (запрещено хардкодить gold-запросы в `seed_glossary`).
- **Синтетический набор (400–600 запросов):**
  - `SYN-A` (300–500 запросов): детерминированная генерация из фида по шаблонам (без LLM) — точные имена, бренд+атрибут, generic-тип, опечатки, транслит, раскладка, склейки/расклейки, числовые, out-of-catalog. Метки известны по построению.
  - `SYN-B` (50–100 запросов): сложные запросы (NL-задачи, сленг, аббревиатуры, омонимы, аналоги), сгенерированные отдельной LLM.
- **Разметка и аудит (вместо двойного слепого аудита с $\kappa$ Коэна):** прогон `LLM-judge` по top-5 выдачи на `SYN-B` + выборочная ручная проверка 30–40 запросов глазами.
- **Сравнение (4 ключевые точки вместо 10 абляций C0–C9):**
  1. `Legacy` (наивный поиск по подстроке и простому BM25 без морфологии и fuzzy — эмуляция описанного поведения);
  2. `BM25F + Fuzzy` (лексическое ядро);
  3. `Hybrid (+Dense)` (без LLM);
  4. `Full Smart (+LLM QU)`.
- Метрики: `Hit@1`, `Hit@4`, `MRR@10`, `nDCG@10`, доля `hard-null` и `soft-null`, доверительные интервалы Уилсона / бутстрэп.

## 3. Онлайн-пайплайн

### 3.1 Typeahead (каждый символ)

Бюджет на сервере p95 <60 мс. Без LLM и без dense.
- **Клиент:** debounce 80 мс, `AbortController`, sequence-id.
- **T0–T1:** Нормализация, исправление раскладки («ghbdtn»), префикс-поиск по бренду, продукту, алиасу, категории. Fuzzy-префикс через SymSpell при длине ≥3.
- **T2. Товары на лету:** Топ-4 **family** для текущего префикса (миниатюра, имя, «от X ₽», бейдж наличия и акции).
- **T3–T4:** До 3 связанных запросов; chips интентов для известных омонимов («сервер», «мтс», «365»).
- **Пустой фокус:** история пользователя и «популярное» по сегменту.

### 3.2 Полный поиск: шаги S0–S12

Каждый шаг формирует span `{id, title, status, ms, summary, data, decision, fallback_used}`, который стримится по **SSE** и сохраняется для разбора в аналитике.

- **S0. Приём:** `trace_id`, `session_id`, `ctx` (`segment`, `page_category`, `history`), режим (`legacy|smart`), `llm_enabled`. Маскирование PII (email, телефоны, ИНН) до записи в лог.
- **S1. Нормализация:** NFKC, ё→е, исправление гомоглифов (латинская `a` в русском слове), раскладка, дефисные слова (в 2 формах: цельная и раздельная), вынос шумовых слов («купить», «цена»).
- **S2. Токенизация и лемматизация:** pymorphy3 для кириллицы, определение аббревиатур.
- **S3. Генерация гипотез написания (детерминированно):** exact alias, склейка/расклейка («крипто про» → «криптопро», «max patrol» → «maxpatrol»), опечатки (SymSpell), транслит, сленг/синонимы, числовые алиасы. Политика против переисправления: при сильном совпадении оригинала в `name_head` даём «Возможно, вы искали…», иначе автоприменение с плашкой возврата.
- **S4. Понимание запроса (QU):**
  - *Правила:* разметка BRAND, PRODUCT_TYPE, ATTR (срок, qty, лицензия, сегмент, версия), RELATION («для», «под»), MODIFIER («аналог»). Правило голого существительного: голый тип («сервер») означает сам предмет (`name_head`), а не ПО «для» него (`name_target`). Выдаёт распределение вероятностей по интентам.
  - *Эскалация к LLM:* только при низком confidence, NL-запросе (≥4 слов без entity), омониме или 0 результатах. В LLM передаётся закрытый список из ~15 кандидатов-сущностей; таймаут 1,5 с, retry ×1, кэш по `normalized_query + ctx_bucket + overlay_version`.
- **S5. Retrieval (5 параллельных полос → RRF Fusion top-150):**
  - `L1` Entity/alias (exact, prefix, fuzzy, фонетика).
  - `L2` BM25F по полям (`name_head` 3.0, `brand` 2.0, `category_path` 1.5, `aliases` 1.2, `params` 0.8, `description` 0.4, `name_target` 0.3).
  - `L3` Char-3gram.
  - `L4` Dense cosine (top-100).
  - `L5` Type-injection (популярные внутри предсказанных `product_type`).
  - *Мультиинтентность:* если 2-й интент ≥ порога, выдача строится секциями (например, для «сервер»: «Серверное оборудование» — честный пустой блок + `catalog_gap`, «Аренда сервера IaaS», «ПО для серверов»).
- **S6. Контекст:** academic/физлицо понижаются для корпоративного сегмента; `page_category` поднимает свой корень; история и контекст предыдущего запроса в сессии. Вклад персонализации ограничен ±15% от fused-score.
- **S7. Ранжирование (top-150 → top-30):** релевантностные ярусы (T1/T2/T3) + линейная комбинация фич (`availability`, `version_recency`, `segment_fit`, `popularity`, `margin_proxy`, `promo`, `data_quality`, штраф `on_request`). Веса (~6–8 основных коэффициентов) подобраны вручную на dev-выборке и вынесены в конфиг (без Optuna и без cross-encoder rerank). Маржа и акция влияют только внутри полосы близкой релевантности `δ`. После скоринга применяются правила `overlay` (pin/demote/boost).
- **S8. Variant resolution:** выбор лучшего `offer` внутри `family` (доступный, `price>0`, подходящий сегмент/срок/qty/версия) + вывод в карточке осей других вариантов.
- **S9. Композиция и разнообразие:** MMR по бренду/типу (отключён для навигационных запросов). Секции: основные, альтернативный интент, российские аналоги (`is_ru_registry`).
- **S10. Гарантия ≥4 различных family (лестница):**
  1. Снять мягкие ограничения (штраф сегмента, фильтр версии, включить `available=false`).
  2. Расширить гипотезы / взять LLM-рерайты / добавить `analog_of` для top-1.
  3. Fill по `product_type`.
  4. Другие продукты найденного бренда.
  5. Подъём на уровень вверх по дереву категорий.
  6. Dense-ближайшие без порога → статическое «Популярное» по корню.
  Каждая добавленная позиция несёт честный `fill_reason`. Для аналитики фиксируем `hard_null` (0 до лестницы) и `soft_null` (сработали ступени 3+ или низкий confidence).
- **S11. Допродажа и акции:** блоки `complements`, `upsell_to`, `analog_of` с provenance-чипами («по данным вендора: …»). Для `EXTERNAL_PRODUCT` («мдаемон») — честный баннер «В каталоге нет», альтернативы и CTA «Запросить поставку».
- **S12. Сборка ответа:** результаты с `explain` (совпавшие поля и вклад фич), секции, trace, `config_version`, `degradation_level`, `cost_meter`. Запись события в SQLite асинхронно.

### 3.3 Режимы деградации (L0–L3)

| Уровень | Условие | Поведение |
|---|---|---|
| L0 | Всё работает | Полный пайплайн |
| L1 | LLM недоступен, таймаут или исчерпан дневной бюджет | QU только по правилам и кэшу. Сложные запросы идут через dense и type-injection. Баннер в trace |
| L2 | Падение энкодера запроса | Отключается L4 (dense). Остаются L1, L2, L3, L5 |
| L3 | Проблема с overlay или БД | Читаем базовый `IndexState`, отключаем персонализацию и правила |

В админке предусмотрены **chaos-переключатели** («Отключить LLM», «Отключить энкодер») для демонстрации отказоустойчивости в реальном времени. Для страховки от падения всего хоста на питче готовится резервное видео демо (вместо отдельного offline-пакета L4 в SPA).

## 4. Бизнес-аналитика

### 4.1 События и `cost_ledger`

Единый append-only лог в SQLite (WAL) с явным полем `source ∈ {live, simulated, gold_replay}`:
- `search_issued` (query, qu, `hard_null`, `soft_null`, `fill_rung`, латентность по шагам, `config_version`, `cost_meter`), `suggest_shown`/`clicked`, `result_impression`/`click`, `chip_click`, `add_to_cart`/`quote_request`/`order` (mock), `cross_sell_click`, `refine`, `abandon`, `feedback` (👍/👎), `catalog_gap_lead`, `admin_action`.
- Таблица `cost_ledger`: каждый вызов LLM пишет `purpose`, `model`, `tokens_in`, `tokens_cached`, `tokens_out`, `latency_ms`, `cost_micro_rub`, `trace_id`. Это единый источник цифр для расчёта стоимости 1 запроса по шаблону организатора.

### 4.2 KPI и калькулятор бизнес-эффекта (3 сценария вместо Monte Carlo)

- **4 KPI организатора:**
  1. Доля запросов без результата (`hard_null` / `soft_null` на синтетике, Legacy vs Smart — тег `derived`).
  2. Уходы после неудачного поиска (оценка при допущении `p_exit = 30–50%` и события в демо-воронке — `modeled / simulated`).
  3. Конверсия поиска в заказ (демо-воронка симулятора — `simulated`).
  4. Потерянные онлайн-заказы (`modeled`).
- **Калькулятор эффекта (детерминированный, 3 сценария):** вместо Monte Carlo на 10 000 итераций используется наглядный расчёт по формулам с редактируемыми ползунками допущений (`Q = 10–20k/мес`, `f_b = 20–40%`, `f_n` из eval, `CVR_s = 5–10%`, `κ = 0.1–0.6`, `AOV` из распределения цен фида, маржа `m`):
  - `R = Q · (f_b − f_n)` — восстановленные сессии;
  - `ΔOrders = R · CVR_s · (1 − κ)` — дополнительные заказы;
  - `ΔRevenue = ΔOrders · AOV`, `ΔProfit = ΔRevenue · m`.
  Выводится в трёх колонках: **Пессимистичный / Базовый / Оптимистичный** с обязательной подписью `data_tier = modeled`.

### 4.3 Трафик для демо

**Симулятор сессий** (воркер) генерирует реалистичный поток запросов и каскадных кликов по персонам, смешивая пул запросов и переформулировки. Все строки помечены `source=simulated`, живые клики на демо — `source=live`. Из цепочек переформулировок (`q1 → q2 → клик`) автоматически майнятся кандидаты синонимов.

### 4.4 Агент диагностики (упрощённая кластеризация)

Запускается воркером по расписанию или кнопкой «Запустить разбор» в админке:
1. **Отбор неудач:** `hard_null`, `soft_null`, `abandon`, цепочки переформулировок без клика, 👎.
2. **Кластеризация:** простая детерминированная группировка по `query_norm` и отсортированному набору лемм (без HDBSCAN). Вес кластера = частота × оценка потенциального чека.
3. **Диагноз по таксономии R1–R10** (правила + LLM с пакетом evidence):

| Код | Причина | Типичный сигнал |
|---|---|---|
| R1 | Опечатка / транслит / раскладка | Есть близкая entity, исправление не сработало |
| R2 | Нет синонима / сленга / аббревиатуры | OOV-токен рядом с entity, переформулировки с кликом |
| R3 | Бренд не в каталоге | Подтверждён seed вендоров или LLM, offers нет (`EXTERNAL_PRODUCT`) |
| R4 | Нет линейки / редакции / версии | Бренд есть, конкретной линейки нет |
| R5 | Слабая карточка | Низкий `data_quality_score`, конфликты params |
| R6 | Проблема ранжирования | Нужная family ниже топ-10 или демотирована |
| R7 | Неоднозначность интента | Уточнения chips / переформулировки |
| R8 | Потерянный спрос из-за доступности | Family есть, но `available=false` / `price=0` |
| R9 | Не-товарный интент | Вебинар, документация («мтс») |
| R10 | Мусор | NONSENSE |

4. **Контрфактическая проверка (dry-run):** агент через `probe_search` прогоняет проблемные запросы с кандидатным исправлением и прикладывает к тикету реальный dry-run uplift («было 0 → стало найдено на позиции 1»).
5. **Тикеты:** `ADD_SYNONYM`, `ADD_ALIAS`, `CATALOG_GAP`, `FIX_CARD`, `RANKING_RULE`, `AVAILABILITY_ALERT`, `INTENT_DISAMBIGUATION` с адресацией по ролям.

### 4.5 Замкнутый цикл (ручное применение + GOLD10-проверка + откат)

Автоматическое одобрение (`auto-policy`) и сложная система инъекционного авто-отката (`FAULT` + `Regression Guard`) в MVP исключены — ручное управление нагляднее и безопаснее на демо:

```
тикет с dry-run uplift → кнопка «Одобрить и применить» (человек)
→ быстрая проверка на GOLD10 (нет ли поломки базовых запросов)
→ запись в overlay (config_version+1) и hot-swap без рестарта
→ мгновенный replay пострадавших запросов (до/после на экране)
→ при необходимости: кнопка «Откатить версию конфига» в ленте аудита
```

- **Auto-policy:** только для `ADD_SYNONYM` и `ADD_ALIAS` при confidence ≥0,9, положительном dry-run uplift и отсутствии регрессии. Pin/demote/boost и catalog patches всегда проходят человека.
- **Regression guard (≈10 с):** gold-10 (регрессия недопустима), синтетика (допуск ε по nDCG@10 и MRR) и must-improve запросы тикета. Провал — откат указателя версии и запись в аудит.
- **Измерение эффекта:** replay пострадавших запросов на новой версии показывает долю «восстановленных» (hard/soft-null → успех). Дальше pre/post по живому и симулированному трафику. В продакшене это A/B, в демо подпись «до/после».
- **Аудит:** кто, что, когда, до/после, `change_id`, ссылка на тикет.

### 4.6 Интерфейсы под 5 ролей (4 объединённых экрана)

Чтобы не распылять разработку на 7 разрозненных страниц, все 5 ролей закрываются **4 плотными экранами**:

| Экран | Для каких ролей | Что на экране |
|---|---|---|
| **1. Витрина + Trace-drawer** | Покупатель, все на демо | Typeahead с товарами на лету, переключатель персон, тумблер `Legacy / Smart`, сценарная панель (gold-10 + сложные кейсы), секции выдачи, допродажи с provenance, акции, пошаговый SSE Trace-drawer (S0–S12 + вклад фич), side-by-side сравнение Legacy vs Smart |
| **2. 7. **Отказоустойчивость:** нажимаем chaos-тумблер «Отключить LLM» → поиск переключается в L1 и продолжает находить товары.

### 6.3 Краевые случаи и риски

- **Краевые случаи (юнит-тесты и проверки):** пустые/длинные запросы, emoji, prompt injection (запрос всегда в разделителях, ответ LLM ограничен closed-set id), «скачать бесплатно/кряк» (показ легальных триалов и бесплатного ПО каталога), «российский аналог» (буст по `is_ru_registry`), `available=false` / `price=0` в топ-1 (бейдж + доступная альтернатива рядом), дубликаты family, маскирование PII (email, телефон, ИНН) в логах.
- **Риски:**
  - *Gold-target отсутствует в mock-фиде:* проверка в первые 3 часа; отсутствующие переводятся в сценарии `catalog_gap`.

  - *LLM недоступен из РФ:* цепочка провайдеров + кэш + мгновенный переход в L1.
  - *Overfit на 10 gold:* настройка весов только на `SYN-A/B`, gold-10 как якорь.
